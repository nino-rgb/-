# VSPO Live Go版 開発記録（設計判断）

> この文書は今回の設計協議で確定した判断と理由の記録。既存の開発記録に追記する用途を想定。

## レイヤー構成を明確に分離する

**決定:** Handler / Service / Client / Repository / Model / Schedulerを分け、main.goで依存関係を組み立てる。

**理由:** Express版では特に同期処理でScheduler・外部API通信・DB操作などの責務が混在していた。Go版では役割を明確にし、変更の影響範囲を狭め、単体テストやCodexによる段階的実装を進めやすくする。APIの外部仕様を変更することが目的ではない。

## インターフェースを実装側に定義する

**決定:** Service・Repository・Clientは原則として実装側パッケージでインターフェースを公開する。Repositoryは共通インターフェースを複数Serviceで共有する。

**理由:** 第一の目的は、利用側が別レイヤーの具体的な実装を知らずに契約を通じて機能を利用できること。第二の目的はテスト時のモックへの差し替え。利用側に小さなインターフェースを定義するGoの慣習も比較したうえで、今回の学習・設計方針として実装側定義を採用した。将来肥大化した場合は分割を検討する。

## 業務ルールはServiceに集約する

**決定:** 配信情報とタレントの紐づけ、`miss_count`の増減、終了・削除判定はServiceが担当する。RepositoryはSQLとDB整合性の確保を担当する。

**理由:** 三層アーキテクチャの責務分離を優先し、業務ルール変更時にRepositoryのSQLへロジックが散らばることを避ける。RepositoryからのエラーはServiceへ伝播するが、ServiceはDBの実装詳細を知る必要はない。

## トランザクションは各Repository内部で管理する

**決定:** `NowstreamingRepository`と`ArchiveRepository`が、それぞれ一括更新メソッド内でトランザクションを管理する。汎用TransactionManagerは現段階では導入しない。

**理由:** 現在の同期更新はテーブル単位で独立して完結できる。Serviceに`*sql.Tx`を露出せず、汎用的な抽象化の実装負荷も避けられる。将来複数Repositoryをまたぐ原子的更新が必要になれば再検討する。

## 外部API取得はトランザクションの外に置く

**決定:** YouTube/Twitch API取得と検証を完了してからDBトランザクションを開始する。

**理由:** 外部API通信中にDBトランザクションを長時間保持しない。DBロールバックでは外部APIリクエスト自体を取り消せないため。

## 同期処理を独立させる

**決定:** YouTubeライブ・YouTubeアーカイブ・Twitchライブは独立したDBトランザクションで反映する。

**理由:** 片方のAPI取得・DB更新が失敗しても、成功した同期結果は保持するという既存方針を守る。

## 同時配信はDB更新順で上書きする

**決定:** 1タレント1件を維持し、プラットフォーム優先順位は設けず、最後にDBへ正常反映された情報を残す。

**理由:** Express版の意図的な挙動を維持するため。未検出による更新・削除は対象プラットフォームと外部配信IDを条件に含め、別配信への誤操作を防ぐ。

## デッドロックに備える

**決定:** ロック取得順を`talent_id`昇順に統一し、MySQL 1213時は初回を含め最大3回、DB処理全体を再試行する。再試行時はDBを読み直してServiceが再判定する。

**理由:** 同一テーブルへの並行更新で起こり得る競合に対応するため。APIの再取得は不要であり、古いDB状態に基づく削除判定を再利用しない。

## 同期時刻を固定・分散する

**決定:** JST基準でYouTubeは毎時00分、Twitchは毎時30分。両者とも起動時に1回実行し、同一プラットフォームの重複実行はスキップする。

**理由:** 同時のAPI通信・DB更新集中を減らし、サーバー起動時刻に依存しない運用にするため。

## 詳細設計を一部保留する

**決定:** `SELECT ... FOR UPDATE`、UPSERT、分離レベル、存在しない行への同時INSERT等の詳細は実装時に検証する。Service判定コールバックの関数シグネチャは実装前に整理する。

**理由:** 設計段階で100%を固定するより、MySQLの実際の挙動とテスト結果をもとに安全性を確認して決定するため。

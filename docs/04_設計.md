# VSPO Live Go版 設計

> 状態: 基本方針確定。実装詳細は一部保留。
> 対象: Express/TypeScriptバックエンドからGoへのリメイク。既存ReactフロントエンドとのAPI互換を基本とする。

## 1. 設計原則

- 既存の外部API仕様と意図的な挙動を原則維持する。不具合修正・内部設計改善は変更理由を記録する。
- ビジネスロジックはServiceに集約する。「何をするか」はService、「DBでどう実行するか」はRepositoryが担当する。
- 各レイヤーは依存先の具体的な実装ではなく、インターフェースを通じて連携する。目的は実装詳細への依存を減らすことと、テスト時の差し替えを容易にすること。
- 過度な抽象化は避け、詳細な競合制御は実装と検証を通じて決める。

ファイル名は設計案。実装上必要な補助ファイルの追加を妨げない。

| 役割 | 責務 |
|---|---|
| Handler | HTTPリクエストの受信、入力検証、レスポンスへの変換 |
| Service | 業務ルール、タレント照合、配信状態・終了判定、同期処理の制御 |
| Client | YouTube/TwitchとのHTTP通信、認証、レスポンス取得 |
| Repository | DB読み書き、SQL、各テーブルの同期更新トランザクション |
| Model | ドメインデータ構造 |
| Scheduler | 実行時刻、同一プラットフォームの重複起動防止 |
| main.go | 接続・実装の生成、依存性注入、サーバー起動 |

## 3. インターフェースと依存性注入

- Service、Repository、Clientのインターフェースは、原則としてそれぞれ**実装を提供する側のパッケージ**に定義する。
- Repository側には共通インターフェースを用意し、複数のServiceから共有する。ServiceのインターフェースもHandlerやSchedulerから利用する。
- `main.go`が具体的な実装を組み立て、コンストラクタに注入する。DIフレームワークは前提としない。
- インターフェースが肥大化した場合は、必要に応じて分割を検討する。
- Goの`context.Context`をHTTP通信・DB操作・同期処理へ伝播し、キャンセルや期限に対応する。

## 4. 同期処理の責務分担

1. Schedulerが同期Serviceを起動する。
2. ServiceがClientを利用して外部APIから必要な情報を取得し、取得成功を確認する。
3. Repositoryがトランザクションを開始し、必要なDB状態を安全に読み取る。
4. Serviceがその最新状態とAPI結果から、UPSERT・更新・削除対象を判定する。
5. Repositoryが判定結果をSQLで反映し、COMMITまたはROLLBACKする。
6. 同期処理のトランザクションは各Repositoryが管理する｡ただし､コールバックの採用は処理内容に応じて､Nowstreamingでは使用し､Archiveでは使用しない｡

### 4.1 ApplySyncとコールバック

NowstreamingRepositoryにApplySync()を設け、Serviceから判定関数を渡す方式を採用する。

Repositoryはトランザクション内で取得した最新のDB情報をコールバックの引数として渡す。

Serviceは、外部APIから取得済みの情報とDBの最新状態を比較し、更新内容を返す。

コールバック内では外部API通信やDB更新を行わず、判定処理のみを実行する。

RepositoryはServiceパッケージを直接importしない。

具体的な関数シグネチャは実装時に確定する。

### 4.2 NowstreamingSyncResult

Serviceが判断した更新内容は、以下の構造体でRepositoryに渡す方針とする。

```Go
type NowstreamingSyncResult struct {
    Upserts []Nowstreaming
    Missed  []NowstreamingMiss
    Deletes []NowstreamingDelete
}

type NowstreamingMiss struct {
    TalentID         int64
    Platform         string
    ExternalStreamID string
    MissCount        int
}

type NowstreamingDelete struct {
    TalentID         int64
    Platform         string
    ExternalStreamID string
}
```

- Upserts：新規配信、継続配信、miss_countのリセット

- Missed：配信情報の1回目の消失に伴うmiss_count更新

- Deletes：2回連続で配信情報が消失した場合の削除

miss_countの更新後の値はServiceが計算する。

構造体の詳細は実装時に確定する。具体的な関数シグネチャは実装前に検討する。RepositoryがServiceパッケージを直接importする構成は避ける。

## 5. トランザクション

- **外部API取得はDBトランザクション開始前に完了**させる。
- 各Repositoryが、自分のテーブルに対する一括同期更新のBEGIN/COMMIT/ROLLBACKを担当する。
- 現時点では汎用的なTransactionManagerを導入しない。
- YouTubeライブ、Twitchライブ、YouTubeアーカイブのDB反映は**それぞれ独立したトランザクション**とする。
- `nowstreamings`ではUPSERT、`miss_count`更新、終了配信削除を一括反映する。
- `archives`では新規INSERTと14日経過分のDELETEを一括反映する。
- 卒業済みタレントの`nowstreamings`削除は外部APIの成否に依存しない共通クリーンアップとして扱う。
- 将来、複数Repositoryを横断する原子的更新が必要になれば、TransactionManager等を再検討する。

## 6. 配信情報の競合制御

- nowstreamings.talent_idを主キーとし、1タレントにつき配信情報は1件とする。

- YouTube/Twitch間に優先順位を設けず、最後にDBへ正常反映された配信情報を残す。

- 新規配信・継続配信はUPSERTを使用する。

- 配信が継続している場合、Serviceはmiss_countを0に戻すと判断する。

- 配信が1回検出されなかった場合、Serviceはmiss_countの更新後の値を計算する。

- 2回連続で検出されなかった場合、Serviceは削除対象と判断する。

- 未検出配信のUPDATE・DELETEではtalent_id、platform、external_stream_idを条件に指定し、別配信への誤操作を防ぐ。

- RepositoryはServiceの判定結果をSQLで反映する。

- 既存行の確認にはSELECT ... FOR UPDATE等の行ロックを利用する方針とする。

- 複数タレントのロック取得順は原則talent_id昇順に統一する。

- 新規行・並行UPSERTを含む詳細は実装時に検証する。

## 7. デッドロック時の再試行

- MySQLエラー1213（デッドロック）を検出した場合、初回を含め最大3回、DBトランザクション全体を試行する。

- 再試行前に短いランダムな待機を設ける。具体的な時間は実装時に調整する。
 
- 再試行では外部APIを再取得しない。

- 新しいトランザクションでDBの最新状態を取得・ロックし、Serviceから渡されたコールバックを再実行する。

- コールバックは再実行可能な判定処理とし、外部API通信やDB更新などの副作用を含めない。

- context.Contextのキャンセル時は再試行を中止する。

- 上限を超えた場合はエラーを記録し、次回の定期同期に任せる。

- ほかのDBエラーを無条件に再試行しない。

## 8. アーカイブ同期処理

### 8.1 基本方針

- アーカイブはYouTube APIから取得する。
- 既存のアーカイブは保持し、新しく取得したアーカイブのみ追加する。
- APIの取得結果に含まれない既存アーカイブも、保持期間内であれば削除しない。
- 既存アーカイブの全削除・再登録は行わない。
- APIの取得・検証に失敗した場合は、DBを変更しない。
- アーカイブの新規追加と期限切れデータの削除は、同一トランザクションで実行する。

### 8.2 ServiceとRepositoryの責務分担

**Service**
- Clientを利用してYouTube APIからアーカイブ情報を取得する。
- APIの取得成功とデータの妥当性を確認する。
- 取得したアーカイブと登録済みタレントを照合し、保存対象を決定する。
- UTCでアーカイブの削除基準日時を計算する。
- Repositoryの`ApplySync()`を呼び出す。

**Repository**
- トランザクションの開始・確定・ロールバックを管理する。
- UNIQUE制約を利用して重複登録を防止する。
- 新規アーカイブのみINSERTする。
- 保持期間を超えたアーカイブをDELETEする。
- SQL実行時のエラーをServiceへ返す。

### 8.3 重複防止

- `archives.external_stream_id`にUNIQUE制約を設ける。
- 同じ`external_stream_id`を持つアーカイブは重複登録しない。
- 既存アーカイブの情報は原則として更新しない。
- 重複以外のDBエラーを無条件に無視するSQLは採用しない。
- 具体的なINSERT文と重複時の処理は実装時に確定する。

### 8.4 保持期間と削除条件

- アーカイブの保持期間は`open_date`から336時間（14日間）とする。
- 日付のみではなく、時刻まで含めて保持期間を判定する。
- 日時はUTCで扱う。
- `open_date`が削除基準日時より古いアーカイブを削除する。
- 削除基準日時と完全に一致するアーカイブは保持する。

Service側の削除基準日時の計算例：

```go
cutoff := time.Now().UTC().Add(-14 * 24 * time.Hour)
```

Repository側のSQL例：

```sql
DELETE FROM archives
WHERE open_date < ?;
```

### 8.5 ApplySyncとトランザクション

ArchiveRepositoryには、コールバックを使用しない`ApplySync()`を設ける。

想定する関数シグネチャ：

```go
func (r *ArchiveRepository) ApplySync(
    ctx context.Context,
    archives []models.Archive,
    cutoff time.Time,
) error
```

同期処理の流れ：

1. ServiceがYouTube APIからアーカイブ情報を取得・検証する。
2. Serviceがタレント照合を行い、保存対象を決定する。
3. Serviceが削除基準日時を計算する。
4. Repositoryがトランザクションを開始する。
5. Repositoryが新規アーカイブのみINSERTする。
6. Repositoryが保持期間を超えたアーカイブをDELETEする。
7. 正常終了時はCOMMIT、エラー発生時はROLLBACKする。

新規INSERTと期限切れDELETEは、同一トランザクションで実行する。

Nowstreamingとは異なり、Serviceがトランザクション内でDBの最新状態を受け取って業務判断する必要がないため、コールバックは使用しない。

## 9. 実装時の検討・検証事項

### 9.1 Nowstreaming同期処理

- `ApplySync()`の具体的なインターフェースとコールバックの型定義
- `NowstreamingSyncResult`の最終的なフィールド構成
- `SELECT ... FOR UPDATE`の対象行・ロック範囲・トランザクション分離レベル
- 存在しない行へのINSERTと並行UPSERTの競合
- UPSERTと条件付きUPDATE・DELETEの整合性
- UPDATE・DELETEの影響行数が0件だった場合の扱い
- YouTube/Twitchの同時書き込みによる競合と、デッドロック発生時の再試行

### 9.2 Archive同期処理

- UNIQUE制約を利用した重複スキップSQLの具体的な実装
- 同一アーカイブに対する並行INSERT時の動作
- 新規INSERTと期限切れDELETEの原子性
- UTC日時の保存と336時間の保持期間の判定
- API取得・検証失敗時にDBが変更されないこと
- 既存アーカイブが削除・再登録・上書きされないこと（保持期間内のデータが対象）

### 9.3 共通事項

- トランザクション内の処理を短時間で完了させること
- エラー発生時のROLLBACKと、正常終了時のCOMMITの動作
- `context.Context`のキャンセル・タイムアウト時の動作
- 同期処理の異常終了後、次回の定期同期で正常に処理を再開できること

これらの詳細は実装・テスト時に決定する。

ただし、**1タレントにつき配信情報1件、他プラットフォームへの誤更新防止、同期単位の原子性、アーカイブの増分保存と保持期間**という確定要件は維持する。
